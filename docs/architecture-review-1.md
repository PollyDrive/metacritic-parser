1. In-process Scheduler (Критично для надежности и масштабирования)
В plan.md указано, что планировщик работает внутри процесса FastAPI (infrastructure/scheduler/hourly_job.py).

Проблема: Это классический антипаттерн. Если вы решите запустить FastAPI в несколько воркеров (например, через Gunicorn для отказоустойчивости), каждый воркер запустит свой собственный шедулер, что приведет к параллельному дублирующему парсингу. Кроме того, любая тяжелая синхронная задача или утечка в шедулере может заблокировать Event Loop веб-сервера. При рестарте контейнера (например, при деплое) таймер сбрасывается.
Решение: Парсинг должен быть вынесен в отдельный CLI-скрипт (например, консольную команду) и запускаться внешним планировщиком (Cron, Celery beat, или просто отдельным python-процессом while True: sleep()). Веб-сервер должен только читать данные и предоставлять API/UI.
2. Квоты YouTube Data API (Блокер для "Дополнительной части 1")
В tasks.md (T044) предполагается использование YouTube Data API для поиска летсплеев.

Проблема: Метод поиска (search.list) в YouTube Data API "стоит" 100 единиц квоты за каждый запрос. Бесплатный лимит на проект — 10 000 единиц в день. По вашему расписанию: 20 игр в час * 24 часа = 480 игр в день. Это потребует 48 000 единиц квоты только на поиск. Ваш API-ключ будет исчерпывать дневной лимит за первые 4-5 часов работы.
Решение: Либо запрашивать расширение квоты у Google (долго и не факт что одобрят для пет-проекта), либо парсить поисковую выдачу YouTube HTML/через внутренние клиенты (например, используя библиотеку yt-dlp для извлечения метаданных и поиска), обходя официальный Data API.
3. Отсутствие State Machine для пайплайна (Риск потери данных)
Согласно data-model.md, игры не имеют статуса обработки, а опираются на факт наличия в таблице и last_updated_at.

Проблема: Пайплайн состоит из множества шагов, подверженных сетевым сбоям: Scrape Metacritic -> Insert DB -> Call LLM (Critics) -> Call LLM (Users) -> Search YouTube -> Fetch Transcript -> Call LLM (Takeaway). Если процесс упадет на этапе вызова LLM (например, таймаут API) после сохранения игры в БД, то в следующий час скрипт сочтет эту игру "уже обработанной сегодня" и пропустит ее. В итоге в каталоге будут копиться игры без резюме и видео.
Решение: Ввести таблицу или поле статуса конкретно для пайплайна обработки (например: pending_llm, pending_youtube, completed, error). Это позволит реализовать паттерн Idempotent Retry и докачивать недостающие данные.
4. Защита от ботов Metacritic (Риск пермабана IP)
В плане используется обычный httpx и задержка между запросами (delay).

Проблема: Metacritic защищен Cloudflare и агрессивно реагирует на автоматические запросы. Стандартный httpx с дефолтными TLS-отпечатками будет быстро заблокирован (выдаст 403 Forbidden или капчу), особенно при обходе по 20-50 страниц каждый час с одного IP-адреса.
Решение: Архитектуру скрапера нужно спроектировать с учетом обхода защит. Потребуется ротация User-Agent, возможно ротация прокси-серверов, и использование HTTP-клиентов с подменой TLS-fingerprint (например, curl_cffi или эмуляция через Playwright/Selenium).
5. Глубина контекста для LLM (Качество фичи)
В задаче сказано: "Просматривает отзывы и пишет короткое резюме...". В плане указано, что собирается "game detail page".

Проблема: На главной странице игры Metacritic выводит всего несколько (3-4) избранных цитат критиков и пару отзывов пользователей. Если кормить в LLM только этот срез, резюме будет поверхностным и часто необъективным.
Решение: Скраперу придется делать дополнительные HTTP-запросы на страницы /critic-reviews и /user-reviews, чтобы собрать репрезентативную выборку отзывов (хотя бы топ-20). Это еще сильнее увеличивает количество HTTP-запросов и риск бана из пункта 4.
6. Пересечение Similar Games в памяти (Риск Performance)
В FR-016 и T038 указано, что Similar Games вычисляются "at read time" через пересечение массива related_games_raw и наличия игр в каталоге, используя domain/rules.py.

Проблема: Если это реализовано в памяти на Python, приложению придется либо тянуть в память все metacritic_slug из БД, либо делать N запросов для каждой отображаемой карточки.
Решение: Следует убедиться, что логика из domain/rules.py лишь подготавливает ключи, а в репозитории выполняется строгий и быстрый SQL-запрос вида SELECT * FROM games WHERE metacritic_slug = ANY(:slugs) без дополнительной бизнес-логики на уровне Python.
