# Архитектурное ревью: Decayed TTL & Воркеры

В ходе добавления функционала обновления отзывов (Decayed TTL) была допущена сильная фрагментация и дублирование логики между слоями, что нарушает инкапсуляцию и повышает риск блокировки парсера. 

## 1. Дублирование логики обогащения (Critical)

**Где:** `application/ingest.py` (`_summarize_and_store`) и `scripts/run_scheduler.py` (`_run_backfill`).
**Проблема:**
Оба файла содержат идентичный конвейер для скачивания, парсинга и сохранения отзывов:
1. Вызов страницы отзывов (Critic/User).
2. Парсинг через `parser.parse_reviews()`.
3. Обращение к LLM через `summarize_reviews()`.
4. Создание записей `LlmCallORM` и `ReviewSummaryORM`.
5. Обновление поля `next_refresh_at` через `calculate_next_refresh`.

**Почему это опасно:** 
В `run_scheduler.py` (в бэкфилле) запрос за HTML идет напрямую через `http_client.get(...)`, полностью **игнорируя `MetacriticClient`**. 
Из-за этого фоновое обновление отзывов работает без задержек (politeness delay), без повторных попыток при ошибках (retries), без обработки Cloudflare-челленджей и без User-Agent. Это прямой путь к перманентной блокировке IP со стороны Metacritic.

## 2. Нарушение Separation of Concerns (Утечка бизнес-логики)

**Где:** `scripts/run_scheduler.py`
**Проблема:** 
Файл-точка входа (entrypoint), который должен только связывать зависимости и запускать воркер, берет на себя прямую работу с БД. Он сам инстанцирует ORM-модели (`LlmCallORM`, `ReviewSummaryORM`), сам пишет сырые SQL-запросы (`delete(ReviewSummaryORM).where(...)`) и сам пересчитывает дату следующего обновления (`calculate_next_refresh`).

## 3. Мертвый/Избыточный код

**Где:** `application/ingest.py`
**Проблема:**
В `IngestGamesUseCase` теперь смешана логика первичного приема игр и логика их пере-обогащения (проверка `refresh_due` и удаление старых отзывов перед скачиванием новых). Ingest (сборщик) не должен заниматься отслеживанием протухших отзывов — это прямая обязанность Backfill-воркера. 

## 💡 План рефакторинга

Чтобы избавиться от этого технического долга, предлагаю следующие шаги:

1. **Выделить `ReviewEnrichmentUseCase`** 
   Создать новый сервис (например, в `application/enrichment.py`), который будет инкапсулировать весь флоу: удаление старого отзыва (если есть), скачивание через `MetacriticClient`, обращение к LLM, сохранение в БД и пересчет `next_refresh_at`.
   
2. **Очистить `run_scheduler.py`**
   Скрипт воркера должен стать "глупым". В `do_work_for_step` он должен просто вызывать `review_enrichment_use_case.run(game, audience)`.

3. **Упростить `ingest.py`**
   Инжест должен использовать тот же `ReviewEnrichmentUseCase` для свежих игр, вместо хранения копии логики обогащения в `_summarize_and_store`.
